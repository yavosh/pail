# pail v0.1: S3 API on local disk

Date: 2026-10-01. Status: proposed. Tracking issue: #17.

## Goal

pail v0.1 lets the AWS CLI, aws-sdk-go-v2, and boto3 run their common S3 flows
against a local server with default client settings. Common flows are bucket
management, object reads and writes, listing, copy, multi-delete, multipart
upload, and presigned URLs.

pail v0.1 is done when its responses match AWS S3 in a black-box check. A
scenario suite sends the same requests to AWS S3 and to pail and compares the
responses. Every remaining difference is listed with a reason. See
[Validation](#validation).

## Non-goals

- Scale, clustering, replication, or high availability.
- AWS IAM, bucket policies, or ACL enforcement.
- Crash durability. pail does not fsync, because test suites write many small
  objects. Atomic renames still keep every object consistent.
- Feature parity with AWS S3. Unsupported operations fail loudly with
  `501 NotImplemented`, so a test never passes by accident.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Authentication | SigV4 only. One access key pair, set with flags or environment variables. Every S3 request must be signed. | This matches how clients talk to AWS. SigV2 is deprecated, and anonymous access adds policy logic. |
| Region | Default `us-east-1`. The verifier accepts any region in the credential scope. | Local tests often use arbitrary regions. Rejecting a mismatch adds friction and catches no real bug. |
| Addressing | Path-style always. Virtual-hosted-style when `--domain` is set, for example `photos.localhost:9000`. | SDKs default to virtual-hosted-style. Some tools force path-style. |
| Routing | A custom S3 dispatcher splits the decoded `r.URL.Path` into bucket and key. SigV4 builds its canonical request from `r.URL.EscapedPath()`. `http.ServeMux` serves only pail's own endpoints. | `ServeMux` redirects paths that are not clean, such as `a//b` or `../x`. Those are valid S3 keys. |
| Own endpoints | Under `/_pail/`, for example `GET /_pail/health`. | `_` is not allowed in bucket names, so the prefix cannot collide with a bucket. |
| Configuration | Flags and `PAIL_*` environment variables. No config file. | It keeps to the standard library and works well with `docker run -e`. |
| Storage | `internal/store` implements S3 semantics on a small VFS interface. `internal/vfs/localdisk` is the first VFS. | S3 rules live in one place. A new backend only implements file operations. |
| Object layout | Metadata files are named by the SHA-256 of the key. Object bytes live in immutable blob files. | Keys like `a` and `a/b`, or `dir/` and `dir/file`, can coexist. Keys up to 1024 bytes fit in any filename limit. |
| Commit point | Renaming the metadata file into place commits a write. | Readers never see a partial object or new bytes with old metadata. |
| Compatibility oracle | Integration tests use aws-sdk-go-v2. CI smoke tests use the AWS CLI and boto3. | The real clients define compatibility. aws-sdk-go-v2 appears in `go.mod` but is not linked into the binary. |
| Reference implementation | AWS S3, through record and replay. Responses are recorded from AWS on demand and committed as golden files. CI replays them against pail. | AWS defines S3. Open-source servers have their own differences, and MinIO's community edition is archived. Replay keeps AWS credentials out of CI. |

## S3 feature matrix

### v0.1

| Area | Operations and features |
| --- | --- |
| Service | `ListBuckets` |
| Buckets | `CreateBucket`, `HeadBucket`, `DeleteBucket`, `GetBucketLocation` |
| Objects | `PutObject`, `GetObject`, `HeadObject`, `DeleteObject`, `DeleteObjects`, `CopyObject` |
| Listing | `ListObjectsV2`, `ListObjects` (V1): prefix, delimiter, pagination, `encoding-type=url` |
| Multipart | `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListParts`, `ListMultipartUploads` |
| Authentication | SigV4 `Authorization` header, presigned URLs, and streaming `aws-chunked` payloads: signed chunks, unsigned with trailer, and signed with trailer |
| Integrity | `Content-MD5`, `x-amz-content-sha256`, and flexible checksums: CRC32, CRC32C, CRC64NVME, SHA-1, SHA-256 |
| Metadata | `Content-Type`, `Content-Encoding`, `Content-Disposition`, `Content-Language`, `Cache-Control`, `Expires`, and `x-amz-meta-*` |
| Reads | Single `Range`; `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Unmodified-Since`; `response-*` query overrides |
| Conditional writes | `If-None-Match: *` and `If-Match` on `PutObject` and `CompleteMultipartUpload` |
| Errors | S3 XML error bodies with the AWS error codes and status codes; `x-amz-request-id` on every response |

### Later

- `UploadPartCopy`.
- Object tagging and the `x-amz-tagging` header.
- CORS, for browser uploads with presigned URLs.
- Browser form uploads (`POST` object with a POST policy).
- Accept-and-ignore stubs that some tools probe for: canned ACL headers,
  `GetBucketAcl`, `GetObjectAcl`, `GetBucketVersioning`, and SSE-S3 headers.
- More than one access key.
- TLS.
- An in-memory VFS.

### Not planned

Versioning, Object Lock, lifecycle rules, replication, event notifications,
S3 Select, inventory, analytics, static website hosting, access logs, transfer
acceleration, Requester Pays, IAM and bucket policies, SigV2, SigV4a, and S3
Express (`CreateSession`).

## Limits

pail enforces the AWS limits, so code that passes against pail also passes
against AWS.

| Limit | Value |
| --- | --- |
| Bucket name | AWS general-purpose bucket naming rules: 3 to 63 characters, lowercase letters, digits, hyphens, and dots |
| Object key | 1 to 1024 bytes of UTF-8 |
| Single `PutObject` and `CopyObject` | 5 GiB |
| Multipart parts | Part numbers 1 to 10,000. Each part is 5 MiB to 5 GiB, except the last. |
| User metadata | 2 KB |
| Presigned URL lifetime | 7 days |
| Clock skew | 15 minutes |
| `max-keys` | 1000 by default and at most |
| `DeleteObjects` | 1000 keys per request |

## Architecture

```text
cmd/pail             main parses flags and env, then calls run(ctx)
internal/server      listener, http.Server, graceful shutdown, wiring
internal/s3api       S3 dispatcher, handlers, XML types, error mapping
internal/sigv4       SigV4 verification: header, presigned, aws-chunked decoder
internal/store       S3 semantics: buckets, objects, listing, multipart
internal/vfs         the VFS interfaces: FS, File, TempFile
internal/vfs/localdisk  the VFS on local disk, rooted with os.Root
internal/buildinfo   build version
test/                aws-sdk-go-v2 integration tests
```

Each interface lives in the package that consumes it. `s3api` defines the
store interface it needs. The VFS interfaces are the exception: they live in
`internal/vfs`, like `io/fs`, because every backend must return the same
`vfs.File` and `vfs.TempFile` types.

Request flow:

```text
client → server → s3api dispatcher → sigv4 verify → handler → store → VFS → disk
```

## On-disk layout

```text
<data>/
  tmp/                               staging for atomic renames
  buckets/<bucket>/
    bucket.json                      creation time
    objects/<sha256(key)>.json       key, size, ETag, headers, checksums, blob name
    blobs/<id>                       object bytes, immutable once written
    uploads/<upload-id>/
      upload.json                    target key and headers
      <part-number>                  part bytes; part metadata in upload.json
```

A write streams the body to `tmp/` and computes the hashes. It verifies the
hashes and renames the file into `blobs/`. Then it writes the metadata file to
`tmp/` and renames it into `objects/`. That rename is the commit point. Last,
it removes the old blob. A reader that finds its blob gone reads the metadata
again once.

At startup, pail empties `tmp/` and removes blobs that no metadata file
references. One pail process owns a data directory.

## Validation

The differential suite in `test/diff` checks pail against AWS S3 as a black
box. It uses HTTP only.

- **Scenarios** are Go tables of raw S3 requests: method, path, query, headers,
  and body. One SigV4 signer signs them, so both targets receive the same
  request. The suite does not use an SDK, because SDK retries and
  normalization would hide differences.
- **Record:** `go test ./test/diff -record` runs the scenarios against AWS S3
  in `us-east-1`, with credentials from the standard AWS environment
  variables. `aws configure export-credentials` sets them from a profile or
  an SSO login. It creates
  only buckets named `pail-diff-<random>` and deletes them afterward. It writes
  one golden file per scenario to `test/diff/testdata/golden/`. A maintainer
  runs it by hand and commits the golden files.
- **Replay:** `go test ./test/diff` runs the same scenarios against an
  in-process pail and compares the results with the golden files. CI runs
  replay only, so CI needs no AWS credentials.
- **Normalization:** the suite replaces values that change on every run, such
  as request IDs, `x-amz-id-2`, dates, bucket names, upload IDs, owner IDs, and
  continuation tokens. ETags and checksums stay, because they are
  deterministic for the same bytes.
- **Comparison:** status code, S3 error `Code`, a fixed list of headers, and
  the XML body after canonicalization. Error `Message` text is not compared.
- **Known differences:** `test/diff/testdata/known-diffs.txt` lists each
  accepted difference with a reason and an issue link. Anything not listed
  fails the test.

Each feature issue adds its scenarios to the suite. A scenario counts only
after it is recorded against AWS.

## Open questions

- Should the minimum part size of 5 MiB be configurable, so tests can use
  small parts? The AWS limit is the default either way.
- Should pail stub the ACL and versioning APIs in v0.1? Terraform and some sync
  tools call them. Today they are in **Later**.
