# pail SQS and SNS

Date: 2026-10-09. Status: in progress.

## Goal

pail serves a local Amazon SQS and Amazon SNS next to S3. Tests and CI/CD
harnesses can use the AWS SDKs, the AWS CLI, and boto3 against one endpoint.
Like the S3 side, the goal is API compatibility, not scale.

## Non-goals

- Production use, scale, or high availability.
- IAM, queue policies, topic policies, and permission actions.
- SMS, mobile push, platform applications, and data protection in SNS.
- SQS message move tasks.
- The legacy SQS query protocol.
- SNS FIFO topics in v1.

Unsupported actions fail loudly, so a test never passes by accident.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| SQS protocol | AWS JSON 1.0. Requests are `POST /` with `X-Amz-Target: AmazonSQS.<Op>`. Errors also carry `x-amzn-query-error: <Code>;Sender`. | Current SDKs speak it. The service model is `awsQueryCompatible`. |
| SNS protocol | AWS query protocol. Requests are form-encoded `Action=<Op>&Version=2010-03-31`. Responses are XML. | SNS has no JSON protocol. |
| Listener | One listener and one port serve S3, SQS, and SNS. | Clients need one endpoint. |
| Routing | The router reads the service from the SigV4 credential scope. An unsigned request with `X-Amz-Target: AmazonSQS.*` goes to SQS. Everything else goes to S3. | Routing never reads the body. S3 behavior stays unchanged. |
| Authentication | Same access key pair as S3. Header signatures only. The verifier buffers the body and hashes it. | SQS and SNS clients do not send `x-amz-content-sha256`. |
| Persistence | Queue, topic, and subscription definitions persist on disk. Messages live in memory. | Tests recreate messages. A restart keeps the setup. |
| Account ID | `000000000000`. | A fixed value keeps ARNs and queue URLs predictable. |
| v1 features | Standard and FIFO queues, dead-letter queues, SNS topics, SNS-to-SQS delivery, filter policies, and HTTP/HTTPS delivery. | These cover the common test flows. |
| Time | Engines compare `time.Now()` on each call. No background timer per message. | `testing/synctest` can drive all timing. |

## AWS validation stage

Every SQS and SNS PR has an AWS validation stage, as S3 has.

- Each new behavior adds `test/diff` scenarios.
- A maintainer records golden files against real AWS with
  `go test ./test/diff -record`.
- New steps start in `test/diff/testdata/pending.txt`.
- A PR is done when its steps pass and leave `pending.txt`.
- Fix a difference in pail, or list it in `known-diffs.txt` with a reason and
  an issue link.

PR 2 builds this stage. PRs 3 to 8 use it.

## Unverified

PR 1 writes these from memory. PR 2 records them against AWS and fixes pail
where they differ.

- Auth error types and codes, for example `MissingAuthenticationToken`,
  `InvalidClientTokenId`, and `SignatureDoesNotMatch`.
- Legacy SQS query error codes in `x-amzn-query-error`.
- The shape of empty responses.
- Whether `MD5OfMessageAttributes` on a filtered receive covers only the
  returned attributes.
- Whether an old receipt handle stays valid after a new receive.
- Which HTTP failures AWS retries on delivery.
