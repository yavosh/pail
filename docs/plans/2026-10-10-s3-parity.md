# S3 parity

Date: 2026-10-10. Status: in progress.

## Goal

Close the S3 gaps that `findings.md` lists. Options that pail used to ignore
either work as on AWS or fail loudly. The most useful missing APIs and feature
families follow.

## Approach

- Each PR starts with a `test/diff` scenario recorded against AWS, then makes
  pail match it. A difference that pail keeps on purpose goes in
  `known-diffs.txt` with a reason.
- A step names extra response headers to compare in `step.compare`, so older
  golden files stay valid.
- Each PR stacks on the one before it, so work continues while a PR waits for
  review.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Server-side encryption | Accept `AES256`, `aws:kms`, and `aws:kms:dsse`, store the value, and return it. Without a request header, return `AES256`. pail does not encrypt. | AWS encrypts every object by default, and a client sees only the header. |
| SSE-C | Answer `403 AccessDenied`. | AWS blocks SSE-C on new buckets (recorded). |
| Object Lock | Object Lock headers answer `400 InvalidRequest`, as on a bucket without Object Lock. Creating a bucket with Object Lock answers `501 NotImplemented`. | pail has no Object Lock buckets. |
| Checksums | Add SHA-512, MD5, and XXHASH64. XXHASH3 and XXHASH128 answer `501 NotImplemented`. An unknown algorithm answers `400 InvalidRequest`. | The standard library covers SHA-512 and MD5, and XXHASH64 is small. |
| Storage classes | Store and return the class. A `GET` of `GLACIER` or `DEEP_ARCHIVE` answers `403 InvalidObjectState`. There are no transitions and no restore. | Clients see the class in headers and listings. |
